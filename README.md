# Azure Media Pipeline (Monorepo)

This repository contains an end-to-end Azure media processing pipeline.

## Projects

- **MediaGateway.Api** (ASP.NET Core)
  - Issues SAS URLs to allow clients to upload media to **raw-media** container securely.

- **media-processor** (Azure Functions .NET isolated)
  - **Service Bus trigger** consumes events and copies blobs from **raw-media** to **processed-media**.

## Architecture

See: `infra/diagrams/architecture.mmd`

High-level flow:

1. Client requests upload initialization from **MediaGateway.Api**
2. API returns a **SAS URL**
3. Client uploads file to **raw-media**
4. **Event Grid** publishes blob-created event
5. Event is forwarded to **Service Bus** queue `q-media-processing`
6. **Azure Function** processes the message and moves/copies file to **processed-media**

## Local run

### Prerequisites
- .NET SDK
- Azure Functions Core Tools
- Azure CLI (`az login`)

### Notes
- `local.settings.json` is **not committed**
- If local Functions host is running, it may consume Service Bus messages (Azure invocations may not appear)

## Why this design?

This pipeline is designed with **scalability**, **security**, and **loose coupling** as first-class concerns.

The goal was not just to make the system work, but to make it **resilient under load**, **easy to extend**, and **safe to operate** in a real production environment.

Every architectural choice below is intentional and based on common issues observed in cloud-based media systems.

---

### Why SAS URLs for uploads?

Instead of uploading large media files through the API, clients upload files **directly to Azure Blob Storage** using **short-lived SAS URLs** generated by the API.

**Benefits:**

- The API never handles large payloads, keeping CPU and memory usage low
- Uploads are not bound to HTTP request lifetimes
- Permissions are tightly scoped (write-only, container-specific, time-limited)
- Storage scales independently of the API, improving overall throughput

**Alternative considered:**  
Uploading files directly through the API.

**Why it was rejected:**  
This approach does not scale well, introduces unnecessary pressure on the API, and increases the risk of timeouts and failures for large uploads.

---

### Why Event Grid + Service Bus (instead of a direct trigger)?

Blob Storage events are published to **Event Grid**, then forwarded to **Service Bus** before being processed by the Azure Function.

While Azure Functions can be triggered directly from Event Grid, this setup was intentionally avoided.

**Event Grid alone:**

- Guarantees at-least-once delivery, but offers limited retry control
- Does not provide consumer-level dead-lettering
- Has limited buffering when downstream systems are unavailable

**Why Service Bus is added:**

- Durable message storage
- Controlled retry policies and backoff strategies
- Dead-letter queue (DLQ) support
- Ability to add new consumers without changing event producers

This results in a **buffered**, **decoupled**, and **more resilient** event-driven architecture.

---

### Why asynchronous processing?

Media processing is handled **asynchronously** using Azure Functions.

Media-related operations are typically **I/O-heavy and time-consuming**. Running them synchronously would block API responses and degrade user experience.

**Asynchronous processing allows:**

- Immediate API responses
- Graceful handling of traffic spikes
- Horizontal scaling based on queue depth
- Better fault isolation between user-facing and background workloads

The API remains responsive while background processing continues independently.

---

### Why this separation of responsibilities?

The system is intentionally split into two distinct components:

**MediaGateway.Api**
- Handles authentication and authorization
- Issues upload permissions (SAS URLs)
- Has no knowledge of how media is processed

**media-processor**
- Listens to Service Bus messages
- Performs media-related processing tasks
- Has no dependency on client-facing concerns

**This separation:**

- Enforces the single-responsibility principle
- Allows independent scaling and deployment
- Makes future extensions straightforward (e.g. transcoding, thumbnails, AI analysis)
- Reduces coupling between user workflows and background processing
